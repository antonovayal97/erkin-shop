# Миграции базы данных

Проект использует SQLite (`@payloadcms/db-sqlite`, адаптер на базе Drizzle).

## Две схемы работы

- **Разработка (`npm run dev`)** — включён режим `push`: Payload автоматически
  синхронизирует схему `shop.db` с конфигурацией коллекций при старте сервера.
  Никаких команд миграций локально выполнять не нужно.
- **Продакшен (VPS, `NODE_ENV=production`)** — push **выключен**. Схема
  поддерживается только миграциями из `src/payload/migrations/`.
  Невыполненные миграции применяются автоматически при старте сервера
  (`prodMigrations` в `src/payload/config.ts`) — достаточно перезапуска.
  Альтернатива на VPS: `npm run db:migrate` вручную (или в деплой-скрипте).

## Скрипты

| Команда                 | Что делает                                                        |
| ----------------------- | ----------------------------------------------------------------- |
| `npm run db:migrate`    | Применить невыполненные миграции к БД из `DATABASE_URL`/`shop.db` |
| `npm run db:migrate:status` | Показать, какие миграции выполнены / ожидаются                |
| `npm run db:migrate:create имя` | Сгенерировать новую миграцию из изменений коллекций      |

Все команды сами находят конфиг (`@payload-config` в `tsconfig.json`) и загружают
`.env.local` так же, как Next.js.

## Существующие миграции

- `20260924_000000_add_active_columns.ts` — добавляет колонку `active`
  (чекбокс деактивации) в таблицы `categories` и `products` на боевой БД.
  Безопасна на всех окружениях: существование колонки проверяется через
  `PRAGMA table_info`, существующие строки получают `active = 1` (visible).

## Типовой workflow при изменении коллекций

1. Изменить `src/payload/collections/*.ts`.
2. Запустить `npm run dev` — push сам добавит колонки в локальный `shop.db`,
   проверить поведение.
3. Создать миграцию для прода: `npm run db:migrate:create add_something`.
   Будут созданы `XXX_add_something.ts` (SQL-изменения) и
   `XXX_add_something.json` (снапшот схемы для будущих диффов) — файлы
   коммитятся; `index.ts` Payload перегенерирует сам.
4. Проверить сгенерированный `.ts` — Payload рекомендует вычитывать SQL перед
   коммитом.
5. Задеплоить и перезапустить сервер на VPS — миграция применится при старте
   (или выполнить `npm run db:migrate` на VPS).

### Важно: первый baseline-снапшот

Первая команда `migrate:create` в проекте сравнит схему с **пустым** снапшотом
(миграции до этого создавались push-режимом), поэтому сгенерирует полный
`CREATE TABLE` на все таблицы. Чтобы он не падал на существующих БД:

1. Выполнить `npm run db:migrate:create baseline`.
2. **Оставить** рядом созданный `.json` — он станет корректной базовой точкой
   для всех будущих диффов.
3. В созданных `.ts` внутри `up()` удалить `CREATE ...` (заменить на пустое
   тело) — схема уже существует во всех окружениях, миграция нужна только
   как отметка baseline.
4. Задеплоить: на боевой БД она применится как no-op.

После этого все последующие `migrate:create` будут генерировать только реальные
diff-изменения.

### Не смешивайте push и migrate на одной БД

Не запускайте `npm run db:migrate` против локального `shop.db`, созданного
push-режимом: Payload найдёт dev-запись в `payload-migrations` и предупредит о
возможной потере данных. Локальная БД — «песочница», синхронизируется push'ем.
